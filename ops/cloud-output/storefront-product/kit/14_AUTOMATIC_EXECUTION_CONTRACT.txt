AUTOMATIC EXECUTION CONTRACT

The main product is automatic. Once setup and the account tests pass, the agent chooses the next looks, sources qualifying products, records the buyer's authorized links, creates or updates the per-look destination, makes the paired images, writes copy, schedules through the approved publishing route and reconciles the result. The buyer does not stock a weekly product sheet or create every Idea List.

Credit-saving, manual and mixed routes are optional customer choices. Do not silently convert an automatic setup to one of them when access fails. Preserve the automatic queue and report the exact blocked capability.
Before assigning a browser/UI task to the customer, offer to perform it through an available permitted browser route or let the customer do it manually to save credits. State any required connection/provider-permission prerequisite honestly. After a manual choice, supply exact instructions and prepared copy, preserve completed writes, record the choice for that step and wait for its result before dependent actions. A step-specific manual choice does not change the overall automation mode.
Every unresolved client-facing result must lead to a concrete resolution: execute and verify an already-authorized repair; ask for the exact changed choice or required permission; or explain why the customer must act and give the exact steps and completion check. Continue independent authorized work while waiting. A blocked state belongs in the records and must never be the only ending of a client response. Do not present customer approval as a substitute for a provider's required permission, and do not assign manual work that an available authorized operator can perform.

CAPABILITY TESTS
Save CAPABILITIES with action, operator, service, account, access method, terms/permission evidence, tested_at, result, readback evidence and whether the scheduled runtime can use it. A connector being installed is not proof of any particular action.
Test product discovery, qualification, authorized link creation/capture, destination creation, destination updates and readback separately. Use documented Amazon Creators API where eligible. A supported signed-in browser operator may handle only account actions permitted by the applicable service terms and the customer's authorization. Do not scrape, use hidden endpoints, evade detection, or assume browser permission from a successful page load. Creators API catalog access does not establish Idea List write access. A submitted Idea List awaiting approval is not a published destination; reconcile the recorded list in the supported management interface and verify published contents before scheduling a Pin. Do not repeat an uncertain submission or treat creation as an update/runtime pass.
API provisioning, secure credential storage, authentication and catalog eligibility are separate tests. Keep secrets out of chat, tool results, screenshots, logs and repository files; establish supported encrypted storage before generation and verify it without displaying values. An exposed credential must be revoked and replaced through the required approval flow before use. A new-credential AssociateNotEligible result during the provider's review window stays unverified, with the creation time and next eligible retry saved. Reuse the credential, continue independent permitted checks and preserve the requested AUTOMATIC mode; do not create repeated keys or claim unattended sourcing from an interactive authentication pass.
Choose one operator per external write. Save the handoff packet and returned object ID in the shared state. A second agent must not duplicate a claimed write. Cloud runtime is valid only if every required step is available there. Local browser steps require the computer and application to be available. A mixed runtime needs a tested persistent handoff, not a promise that another tool will eventually do it.

PUBLISHING PERMISSION
AUTOMATIC records the customer's production scope. It does not replace a platform's consent requirements. Record PUBLISHING_PERMISSION_EVIDENCE for the exact publisher and automation arrangement. Pinterest's developer guidelines require the end user to choose each scheduled Pin. Do not treat blanket approval as evidence of an exception. If the proposed unattended route has no documented compatible permission, retain the automatic production queue with error_code publishing_permission_unverified. Review First remains an optional mode; do not relabel it as fully automatic.

SETUP AND ENABLEMENT
The agent owns setup sequencing through verified completion. Each passed test, routine repair, saved record and source commit advances immediately to the next available authorized action; none is a reason to wait for the customer to say continue. Persist the current step, confirmed choices, completed evidence, waiting dependencies and next executable action. A reply to a necessary question or approval resumes the pending action and the rest of setup automatically. Continue independent checks while a provider dependency waits, and end an incomplete setup turn only with the specific necessary customer decision, approval or customer-only action after available authorized work is exhausted. Do not claim background continuation without a supported scheduled mechanism.
Create recurring production tasks PAUSED. Build the first complete look automatically, show the exact test Pin to the buyer, schedule only after its test authorization and read back the schedule. Separately test a controlled scheduled run and reconcile its outputs. Enable ongoing production only after all required capability and permission checks pass. Published and verified require live owning-service evidence; a schedule alone cannot pass the live release gate.

RECONCILIATION
Test board discovery/assignment, scheduled reads, published reads, cancellation and live removal as distinct capabilities. Use supported service UI when no connector action covers a capability and that route is permitted. Missing connector tools do not prove the service lacks the feature. If removal cannot be executed, retain pull_requested and report the blocker. Never mark pulled or verified without readback.

SPENDING
Reserve expected image cost in shared state before submission and account for failed/unknown submissions and retries. Enforce the saved remaining budget in the workflow. A prompt budget is not a provider account spending cap; unrelated provider usage is outside that ledger. No silent upgrades, new permissions or provider/model changes.

RELEASE STATUS
This revision repairs the automatic workflow specification. Full unattended execution remains unverified until the actual account route passes source-to-destination, scheduled execution and live publication tests. Do not advertise a tested cloud Amazon/Idea List capability that has not passed. Do not replace that missing proof with mandatory weekly buyer labor.

CANCELLATION IS A SEPARATE CAPABILITY
During setup, verify that the customer's chosen publisher connection exposes an actual cancel/delete action and that an owned test post can be removed and its absence read back. Schedule and update actions alone do not prove cancellation. If cancellation is unavailable, record the manual pull route in the customer's recipe: the customer removes the exact post in the publisher's planner, then the system verifies its absence. Retain pull_requested until verified; never mark an empty-content update as cancellation. Automatic pulling remains unverified until its exact route passes. Preserve other posts during tests.
